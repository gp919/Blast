## 1. 프로젝트 정의

| 항목 | 내용 |
|---|---|
| 이름 | (미정) |
| 장르 | 2D 사이드스크롤 플랫포머 + 근접 전투 |
| 인원 | 2인 코옵 (최대 4인 확장 여지) |
| 엔진 | Unity 6 LTS (6000.x), Universal 2D (URP 2D Renderer) |
| 언어 | C# |
| 네트워크 | Netcode for GameObjects 2.x + Unity Transport |

| 기간 | 약 12주 |

### 이 프로젝트가 증명하려는 것

기존 포트폴리오(DX9/DX11 자체 엔진 3종)로 C++ 기초와 엔진 구조 이해는 이미 증명됨.
따라서 이 프로젝트의 한계 가치는 아래 세 가지에 집중합니다.

1. 상용 엔진(Unity) 워크플로 습득 능력
2. **게임플레이 네트코드 직접 구현** — 예측, 재조정, 보간, 랙 보상
3. AI 도구를 통제해서 활용한 개발 경험

콘텐츠 분량이 아니라 네트워크 품질로 평가받는 프로젝트입니다.

## 2. 확정된 설계 결정과 근거

"더 쉬운 방법이 있다"는 제안이 나오면 이 표를 근거로 판단합니다.

| 결정 | 근거 | 버린 대안 |
|---|---|---|
| Rigidbody2D 대신 BoxCast 커스텀 컨트롤러 | 재조정 시 되감기 재시뮬레이션이 필요한데, Unity 물리엔진은 내부 접촉 캐시까지 완전 복원되지 않아 결정성이 깨짐 | Rigidbody2D + `Physics2D.simulationMode = Script` |
| Input / Simulation / Presentation 3계층 분리 | 입력 읽기와 상태 갱신이 한 함수에 섞이면 특정 틱으로 되감아 재시뮬레이션할 수 없음 | 튜토리얼식 단일 `Update()` 구조 |
| 고정 틱 누산기 루프 | 프레임레이트와 무관하게 동일한 시뮬레이션 결과가 나와야 예측 결과와 서버 결과가 일치함 | `Time.deltaTime` 기반 가변 스텝 |
| NGO 채택 | 공식 패키지라 문서와 도구(Profiler, Simulator, MPPM)가 갖춰져 있고, 예측·재조정을 직접 구현할 여지를 남겨둠 | Photon Fusion 2 (예측·롤백 내장이라 직접 구현할 것이 없음), Mirror |
| NetworkTransform 미사용 (최종) | 위치 동기화를 직접 구현해야 보간 버퍼와 대역폭 최적화를 어필할 수 있음 | NetworkTransform 사용 |
| 직접 IP 접속 | Relay/Lobby는 기술적 학습 가치가 낮고 일정만 소모 | Unity Relay, Lobby 서비스 |
| Input System 폴링 방식 | 고정 틱 시뮬레이션에는 이벤트 콜백보다 폴링이 맞음 | 이벤트/콜백 방식 |
| **float 사용, 고정소수점 미도입** | 서버 권위 + 재조정 구조라 lockstep 수준의 비트 단위 결정성이 불필요. 같은 빌드끼리는 float 결과가 일치하고, 어긋나도 재조정이 수렴시킴 | 고정소수점 수학 라이브러리 |
| **시뮬레이션 틱레이트 60Hz** | 근접 전투 판정과 랙 보상 rewind의 정확도가 히트박스 히스토리의 시간 해상도에 직접 묶임. 30Hz면 100ms 공격이 3틱뿐이라 되감기 대조가 거칠어짐. 대역폭은 스냅샷 레이트를 분리해 따로 통제하므로 틱을 낮출 이유가 없고, 재시뮬레이션 비용은 2~4인 2D kinematic 컨트롤러에서 무시할 수준 | 30Hz |

## 3. 아키텍처

### 어셈블리 구조

```
Assets/Scripts/
  Core/          공용 타입, 수학 유틸, 링버퍼
  Simulation/    결정적 시뮬레이션. UnityEngine 의존 최소화
  Presentation/  렌더링, 애니메이션, 카메라
  Input/         입력 수집 및 버퍼링
  Network/       NGO 연동, 스냅샷, 예측 및 재조정
  Game/          합성 루트. 틱 드라이버, 부트스트랩, 계층 간 배선
  Editor/        에디터 전용 툴. 커스텀 인스펙터, 검증 창. 빌드에 포함되지 않음
```

참조 방향은 단방향입니다.

```
Game -> Network      -> Simulation -> Core
     -> Presentation -> Simulation -> Core
     -> Input        -> Core
```

역방향 참조는 만들지 않습니다. asmdef로 컴파일러가 강제하게 둡니다.
`tools/check-layering.ps1` 이 이 그래프를 기계적으로 검증합니다.

### 합성 루트가 따로 있는 이유

고정 틱 드라이버는 벽시계 시간을 읽어 누산해야 하므로 `Time.deltaTime` 이 필요합니다.
그런데 Simulation 계층은 `Time` 사용이 금지라 드라이버가 Simulation 안에 들어갈 수 없습니다.
역할을 이렇게 나눕니다.

- `Simulation` — 틱 인덱스와 고정 dt만 받아 상태를 전이시킵니다. 시간 개념이 없습니다
- `Game` — 벽시계를 읽어 이번 프레임에 몇 틱 돌릴지 계산하고, Input 에서 입력을 모아
  Simulation 을 N번 진행시킨 뒤, 남은 알파를 Presentation 에 넘깁니다

Input 과 Simulation 을 동시에 참조해야 하는 코드는 전부 여기 둡니다.
`Game` 을 참조하는 어셈블리는 없습니다. 최상위 한 곳이므로 단방향 원칙이 유지됩니다.

### 관측 가능성

**구현한 기능은 눈이나 테스트로 확인할 수 있어야 완료입니다.** 확인 수단이 없으면
동작한다고 믿을 근거가 없고, 나중에 깨져도 알아채지 못합니다. 특히 네트코드는 증상이
간헐적이고 재현이 어려워서, 관측 수단 없이는 디버깅 자체가 성립하지 않습니다.

기능마다 아래 중 최소 하나를 갖춥니다.

| 대상 | 수단 | 예 |
|---|---|---|
| 순수 로직 | EditMode 테스트 | 누산기 시간 보존, 상태 전이 결정성 |
| 런타임 상태값 | Inspector 읽기 전용 표시 | 접지 여부, 현재 틱, 속도, 알파 |
| 공간적인 것 | Scene 기즈모 | 충돌 박스, 캐스트 방향, 접지 프로브 범위 |
| 시간에 따라 변하는 수치 | 화면 오버레이 | RTT, 대역폭, 예측 오차, 재조정 발생 빈도 |

제약이 둘 있습니다.

- **관측 코드가 시뮬레이션에 영향을 주면 안 됩니다.** 읽기 전용이어야 하고,
  매 프레임 호출되는 경로라면 GC 할당도 없어야 합니다
- **시뮬레이션 상태를 `[SerializeField]` 로 노출하지 마세요.** 씬 파일에 런타임 값이
  저장되어 YAML 이 오염되고, 에디터에서 실수로 바꾼 값이 그대로 남습니다.
  `CustomEditor` 로 읽기 전용 패널을 그리는 쪽을 씁니다

관측 수단 자체가 포트폴리오 산출물입니다. 7번의 디버그 오버레이 항목을 참조하세요.

**MPPM 가상 플레이어는 별도 프로세스입니다.** 메인 에디터의 Inspector 나 EditorWindow 는
호스트 인스턴스만 봅니다. 클라이언트에서 예측이 어떻게 어긋나는지는 그 창으로 보이지
않습니다. 따라서 플레이어가 2명이 되는 2주차부터는 **런타임 화면 오버레이가 필수**입니다.
오버레이는 매 프레임 호출 경로이므로 문자열 연결로 인한 GC 할당에 주의하세요.

### 애니메이션은 상태에서 파생시킵니다

Presentation 은 `PlayerState` 를 읽어 Animator 파라미터를 세팅합니다.
시뮬레이션이 이벤트를 쏘고 애니메이션이 그것에 반응하는 구조를 만들지 마세요.

재조정 때문입니다. 서버 보정을 받으면 시뮬레이션이 과거 틱으로 되감겨 다시 실행됩니다.
이벤트 기반이면 되감기 구간의 점프가 재생될 때마다 트리거가 다시 발사되어, 한 번 뛴
점프에 모션과 효과음이 여러 번 나옵니다. RTT 150ms 에 60Hz 면 매 보정마다 9틱이
재생되므로 상시 발생합니다. 상태에서 파생시키면 되감기가 몇 번이든 최종 결과가 같습니다.

`IPlayerPresenter.Render(previous, current, alpha)` 가 상태만 받고 이벤트를 받지 않는
것이 이 규칙을 인터페이스 수준에서 강제한 결과입니다.

### 계층 책임

| 계층 | 하는 일 | 금지 |
|---|---|---|
| Input | 입력 읽기, 시퀀스 번호 부여, 링버퍼 저장 | 캐릭터 상태 직접 변경 |
| Simulation | 고정 틱 단위 상태 갱신 | `Time.deltaTime`, `Transform`, `Animator` 참조 |
| Presentation | 상태 읽어 Transform/Animator 반영, 프레임 보간 | 상태 변경, 이벤트 기반 애니메이션 트리거 |
| Network | 스냅샷 송수신, 예측 실행, 재조정 트리거 | 게임 규칙 판단 |

### Simulation 계층 결정성 규칙

- `Time.deltaTime`, `Time.time` 사용 금지. 틱 인덱스와 고정 dt만 사용
- `UnityEngine.Random` 사용 금지. 시드 기반 자체 난수만
- `Transform`, `Animator`, `Rigidbody2D` 참조 금지
- `Physics2D` 캐스팅 API는 허용 (읽기 전용 질의). 자동 시뮬레이션 의존은 금지
- 순회 순서가 비결정적인 자료구조(`Dictionary` 순회 등)에 로직 의존 금지
- **틱은 정수 카운터가 진실입니다.** 누적된 float 시간을 상태 식별자로 쓰지 마세요.
  `1f/60f`는 float으로 정확히 표현되지 않아(`0.016666668`) 60번 더하면 `1.0000001`이
  됩니다. 누산기는 이번 프레임에 몇 틱을 돌릴지만 계산하고, 시뮬레이션 상태는 `uint tick`
  으로만 식별해야 재조정 시 특정 틱을 지목할 수 있습니다
- **튜닝 값은 전부 초당 단위로 정의합니다.** 중력을 "틱당 0.5"가 아니라 "초당 -30
  units/s^2"으로 두고 `FixedDeltaTime`을 곱하세요. 틱당 단위로 박으면 틱레이트 변경이
  사실상 불가능해집니다

**검증법**: Simulation 어셈블리에서 위 금지 심볼 참조가 0건인가?

## 8. 미결 사항

- 프로젝트 이름
- **다중 플레이어 구조** — 2주차 NGO 스폰 방식을 본 뒤 결정. 방향은 정해져 있음:
  `PlayerState` 하나가 아니라 `WorldState { uint Tick; PlayerState[] Players; }` 로
  승격해야 함. 이것이 스냅샷 단위이자 3주차 링버퍼의 원소가 됨.
  NGO 의 `OwnerClientId` 는 `ulong` 이고 희소해서 배열 인덱스로 쓸 수 없으므로,
  서버가 `clientId -> 0..N-1` 매핑을 할당하고 모든 피어가 같은 매핑을 공유해야 함.
  순회 순서는 인덱스 오름차순 고정 (순서가 결과를 바꾸는 경우 갈라짐).
  미리 만들지 말 것. 쓰지 않는 추상화만 남음
- 캐릭터 수와 역할 구분 여부
- 전투 액션 구성 (기본 공격, 대시, 방어 등)
- 스테이지 수와 승패 조건
- 최종 인원 (2인 고정 vs 4인)
- 자체 트랜스포트 교체 (스트레치 목표) 착수 여부

## 10. GitHub 운영 규칙

### 계층 구조

```
마일스톤 (시스템 단위, 데모 가능한 결과물)
  └ 이슈 (기능 구현 단위)
      └ 브랜치 1개
```

### 마일스톤

- 단위는 **시스템**입니다. 주차가 아닙니다. 일정이 밀려도 구조가 흔들리지 않습니다
- 완료 조건을 설명(description)에 반드시 적습니다. 무엇이 되면 닫는지가 없으면 계속 열려 있습니다
- **미리 다 만들지 않습니다.** 현재 진행 중 + 다음 것까지 최대 2개만 열어둡니다
- 완료 시 닫으면서 `project_context.md` 5번(진행 상태)과 6번(확정 수치)을 갱신합니다

예시 (착수 시점에 생성)

| 마일스톤 | 완료 조건 |
|---|---|
| M1 프로젝트 기반 | 3계층 분리 + 고정 틱 루프 + BoxCast 컨트롤러 동작 |
| M2 NGO 최소 동기화 | MPPM 2인 접속, 지연 조건 문제 영상 확보 |
| M3 클라이언트 예측 | 입력 버퍼 + 로컬 즉시 시뮬레이션 |
| M4 서버 재조정 | 불일치 시 되감기 재시뮬레이션, divergence 수렴 확인 |

### 이슈

**분할 기준** — 아래를 모두 만족하는 크기로 쪼갭니다.

- 반나절 ~ 2일 작업량
- 완료 판정 기준이 하나로 명확함
- 머지해도 빌드가 깨지지 않음
- 브랜치 하나에 대응됨

예: "BoxCast 컨트롤러 구현"(X, 너무 큼) → "수평 이동 캐스트 및 충돌 보정"(O),
"수직 이동 및 지면 접촉 판정"(O), "코요테 타임"(O)

**생성 시점** — 작업 **시작 전**에 만듭니다. 끝나고 소급 생성하지 않습니다.
이슈 없는 커밋은 만들지 않습니다.

**본문 형식**

```
## 목표
(무엇을 되게 하는가)

## 접근
(어떻게 구현할 것인가. 선택지가 있었다면 왜 이걸 골랐는지)

## 완료 조건
- [ ] 검증 가능한 항목

## 참고
(문서 링크, 관련 이슈)
```

"접근" 항목이 핵심입니다. **이슈 히스토리가 곧 설계 근거 기록**이 되고,
나중에 기술소개서와 면접 답변의 1차 자료가 됩니다.

### 라벨

| 종류 | 라벨 |
|---|---|
| 계층 | `core` `sim` `net` `present` `input` `tool` |
| 유형 | `feat` `fix` `refactor` `perf` `docs` `test` `chore` |
| 특수 | `portfolio` (영상·수치 등 산출물 확보 필요), `blocked` |

`portfolio` 라벨은 7번 산출물 표와 연동합니다. 그 시점을 놓치면 나중에 복원이 어렵습니다.

### 브랜치

```
<유형>/<이슈번호>-<짧은-영문-설명>
```

예: `feat/12-horizontal-cast-resolve`, `fix/28-reconcile-tick-offset`,
`tool/35-divergence-overlay`

- `main` 직접 커밋 금지. 항상 브랜치를 거칩니다
- 이슈 1개 = 브랜치 1개 = PR 1개
- 머지 후 브랜치 삭제
- 씬/프리팹을 동시에 수정하는 브랜치를 **병렬로 두지 않습니다.**
  YAML 충돌은 해결이 사실상 불가능합니다. 1인 개발이므로 순차 진행이 원칙

### 커밋

```
<유형>(<범위>): <한글 요약>

(필요 시 본문)

Refs #12
```

예: `feat(sim): 수평 이동 캐스트 및 충돌 보정 구현`

- 유형: `feat` `fix` `refactor` `perf` `docs` `test` `chore`
- 범위: `core` `sim` `net` `present` `input` `tool`
- 이슈 종료는 PR 본문에서 `Closes #12`로 처리. 개별 커밋에 넣지 않습니다
- **`.cs`와 `.cs.meta`는 항상 함께 커밋합니다.** meta 누락은 참조가 깨지는 원인입니다

### PR

1인 개발이라 리뷰어는 없지만, PR 본문은 남깁니다.

```
## 변경 사항
## 검증 방법
## 특이사항 / 판단 근거

Closes #12
```

Squash merge를 기본으로 합니다. 커밋 이력이 이슈 단위로 정리됩니다.
