# AI 협업 로그

AI 도구를 개발에 활용하면서, **출력이 틀렸던 것과 그것을 어떻게 찾아 고쳤는지** 기록합니다.

"AI로 빠르게 만들었다"는 누구나 하는 말이라 어필이 약합니다.
**출력의 오류를 기술 이해로 잡아냈다**는 사례가 AI 친숙도와 기초 실력을 동시에 증명합니다.
자소서와 면접에서 쓸 근거를 여기에 모읍니다.

## 기록 기준

- 대상: 설계 판단 오류, 네트코드 로직 오류, 결정성 위반, 성능 함정
- 제외: 오타, 단순 컴파일 에러, API 이름 착오

## 작성 형식

```
### YYYY-MM-DD | 제목

- 맥락: 무엇을 만들고 있었나
- AI 출력: 무엇을 제안했나
- 문제: 왜 틀렸나 (원리 수준으로)
- 발견 경위: 어떻게 알아챘나
- 수정: 어떻게 고쳤나
```

**"발견 경위"를 반드시 쓰세요.** 면접에서 실제로 파고드는 것은 이 부분입니다.

## 기록

### 2026-08-12 | 계층 경계가 asmdef 참조 그래프만으로는 지켜지지 않았음

- 맥락: NGO 스폰된 플레이어를 합성 루트(`Blast.Game`)의 틱 드라이버에 연결하는 중.
  "NGO 의존을 `Blast.Network` 안에 가둔다"를 이슈 #1 부터의 원칙으로 삼고 있었다
- AI 출력: 레지스트리가 `NetworkPlayer`(= `NetworkBehaviour` 파생)를 그대로 상위
  계층에 노출하는 설계. asmdef 참조 방향이 `Game -> Network` 라 규칙에 맞고,
  NGO 타입은 Network 어셈블리 밖으로 나가지 않는다고 설명했다
- 문제: **상속 체인 때문에 성립하지 않는다.** 상위 계층이 `NetworkPlayer` 를 변수로
  잡기만 해도 C# 컴파일러는 멤버 조회를 위해 기반 타입을 끝까지 해석해야 하고,
  그래서 `Unity.Netcode.Runtime` 참조를 요구한다(CS0012). NGO API 를 한 줄도
  쓰지 않아도 마찬가지다. 즉 "가뒀다"는 주장 자체가 틀렸다
- 발견 경위: 프리팹에 컴포넌트를 붙이려는데 Add Component 목록에 `Network Player`
  가 없었다. `.cs.meta` 는 생성되어 있었으므로 임포트는 됐다는 뜻이고, 컴파일이
  실패해 Unity 가 이전 어셈블리를 그대로 쓰고 있는 상황으로 좁혀졌다.
  `check-layering.ps1` 은 통과 상태였다. 참조 그래프는 정상이었고 깨진 것은
  컴파일이었기 때문이다
- 수정: NGO 타입을 상속하지 않는 평범한 클래스 `PlayerHandle` 을 두고, 스폰 시
  NGO 가 아는 값(`OwnerClientId`, `IsOwner`, `GameObject`)을 복사해 레지스트리에
  넣도록 바꿨다. `Blast.Game` 에 NGO 참조를 추가하는 선택지는 채택하지 않았다.
  그 선택은 경계를 지키는 것이 아니라 경계가 무너졌음을 인정하는 것이기 때문이다
- 남는 교훈: 자동 검사(`check-layering.ps1`)가 통과했다고 계층이 지켜진 것은
  아니다. 그 스크립트는 asmdef 참조 방향만 검사한다. **타입 노출면(어떤 타입이
  어셈블리 경계를 넘어가는가)은 검사 대상이 아니다**

### 2026-08-17 | 입력 유실을 지터 탓으로 진단했으나 전송 레이트의 구조적 문제였음

- 맥락: 나이브 위치 동기화(이슈 #7). 서버가 클라이언트 입력을 받아 보관하는 자리를
  큐가 아닌 슬롯 한 개로 두기로 하고, 왜 그것으로 충분하지 않은지를 3주차 입력
  버퍼의 근거로 남기려던 참이었다
- AI 출력: 슬롯이 덮어써지는 상황을 코드 주석에 **"지터가 끼면 같은 입력이 두 틱
  먹히거나 한 틱이 통째로 유실됩니다"** 라고 적었다. 네트워크 상태가 나쁠 때
  가끔 일어나는 일로 설명한 것이다
- 문제: **지터와 무관하게 항상 일어나는 일이었다.** 입력은 시뮬레이션 틱레이트인
  60Hz 로 만들어지는데 NGO 전송 틱은 30Hz 다. 클라이언트가 매 틱 호출한 RPC 가
  두 개씩 묶여 나가고, 서버는 한 프레임에 둘을 연달아 받는다. 그 사이에 서버 틱이
  돌지 않았으면 뒤에 도착한 것이 앞의 것을 덮어쓴다. 즉 정상적인 네트워크에서도 입력의
  절반이 구조적으로 버려진다.

  이동은 연속값이라 마지막 값만 반영해도 차이가 드러나지 않아 증상이 감춰진다.
  점프는 에지 입력이라 그대로 사라진다. 원인이 하나인데 한쪽에서만 보인다
- 발견 경위: 작업자가 "Client 화면에서만 점프가 가끔 씹힌다"고 보고했다.
  **Host 에서 멀쩡하다는 것이 결정적 단서였다.** Host 는 자신이 서버라 RPC 가
  네트워크를 타지 않고 즉시 로컬 실행되고, 그래서 틱마다 입력 송신과 소비가
  정확히 짝을 이룬다. 덮어쓸 여지 자체가 없다. 네트워크 구간이 개입할 때만
  나타난다는 것은 곧 배칭 구간이 원인이라는 뜻이었다
- 수정: 슬롯 대입 시 에지 입력만 OR 로 합쳐 소비 전까지 유지하도록 했다.
  버퍼는 여전히 넣지 않았다. 순서와 시각 정보는 그대로 버리며, 그것을 살리는
  것이 3주차 입력 버퍼다
- 남는 교훈: "가끔 일어난다"는 진단은 그 자체로 의심 대상이다. 두 레이트가
  정수배로 어긋나 있으면 유실은 확률이 아니라 규칙이다. 그리고 **어떤 조건에서
  증상이 사라지는가**가 어떤 조건에서 나타나는가보다 원인을 빨리 좁힌다

### 2026-08-17 | 성격이 다른 두 보간을 하나로 묶어 필요한 쪽까지 제거함

- 맥락: 나이브 위치 동기화(이슈 #7) 구현 중. 예측과 보간을 일부러 넣지 않아
  지연과 끊김을 관측 가능하게 만드는 것이 목표였다
- AI 출력: 렌더 경로를 전부 `Render(state, state, 0f)` 로 바꿨다. 같은 상태를 두 번
  넘겨 알파 보간을 무력화하는 형태다. "보간 없음"이 이슈의 요구사항이므로
  모든 캐릭터에 일괄 적용했다
- 문제: **보간이라는 이름이 같을 뿐 서로 다른 문제를 푸는 둘을 하나로 묶었다.**
  - 틱 알파 보간: 60Hz 고정 틱과 화면 프레임레이트가 맞지 않는 문제. `deltaTime`
    편차 때문에 한 프레임에 틱이 1번, 2번, 0번 도는데 그 편차를 보정하는 것.
    네트워크와 아무 상관이 없고 1주차부터 있던 것
  - 스냅샷 보간: 30Hz 로 도착하는 원격 상태 사이를 메우는 것. 3주차 대상이고
    이번 이슈에서 일부러 비워둬야 하는 자리

  이슈가 요구한 것은 뒤쪽뿐인데 앞쪽까지 제거했다. 그 결과 **서버가 60Hz 로 직접
  시뮬레이션하는 캐릭터마저** 프레임 편차가 그대로 화면에 드러나게 됐다
- 발견 경위: 작업자가 서버 권위 모드에서 캐릭터 이동 시 떨림을 보고했다.
  수신 상태를 그리는 클라이언트 쪽만이라면 30Hz 계단으로 설명되지만, 서버가
  직접 시뮬레이션하는 캐릭터는 그 설명이 성립하지 않는다는 점이 단서였다.
  네트워크 경로가 개입하지 않는 곳에서 나온 증상이라 원인도 네트워크 밖에 있었다
- 수정: 렌더 경로를 시뮬레이션 주체 기준으로 구분했다. 이 피어가 직접 돌리는
  캐릭터는 `Render(previous, current, alpha)` 로 되돌리고, 수신 상태를 그리는
  캐릭터만 보간 없이 그린다. 판단은 `IsSimulatedHere` 하나가 하고 시뮬레이션
  루프와 렌더 루프가 그것을 공유한다
- 남는 교훈: "이 기능을 빼라"는 요구를 받았을 때, 같은 이름으로 불리는 것이
  하나뿐인지 먼저 확인해야 한다. 여기서는 렌더 보간이라는 한 단어 아래
  프레임레이트 문제와 네트워크 문제가 겹쳐 있었다

### 2026-08-27 | 충돌 박스를 못 바꾸는 이유로 대역폭 기준선을 든 것

- 맥락: 캐릭터 애셋을 붙이면서 충돌 박스(0.4 x 0.5)를 그림 크기에 맞출지 논의 중.
  작업자가 "맵 배치도 조작감도 에셋도 아직 확정이 아니니 콜라이더를 스프라이트에
  맞추는 쪽이 맞지 않나"라고 제안했다
- AI 출력: "지금은 바꾸지 마세요"라며 이유 셋을 들었고, 그중 하나가 **"기준선 영상을
  찍기 직전에 이동 감각을 바꾸는 것은 순서가 틀렸다"** 였다. 이슈 #10 의 기준선
  대역폭 측정과 엮어서 설명했다
- 문제: **충돌 박스는 대역폭과 아무 관계가 없다.** 와이어에 실리는 것은 위치
  `Vector2` 와 방향 `sbyte` 뿐이고, 박스 크기는 시뮬레이션 내부 값이라 전송되지
  않는다. 기준선 오염 논거는 **전송 필드를 늘리는 경우**(원격 애니메이션을 위해
  velocity/grounded 를 `NetworkVariable` 에 추가하는 것)에만 성립하는데, 바로 앞에서
  그 논거를 쓴 탓에 박스 크기에까지 잘못 확장했다. 실제 제약은 "모든 피어가 같은
  값을 써야 한다" 하나뿐이고, 그것은 튜닝 애셋 하나로 관리되므로 이미 지켜지고 있었다
- 발견 경위: 작업자가 "내가 0.4 0.5로 맞춘 이유가 뭐였더라"고 되물었다. git 이력을
  뒤져 최초 BoxCast 커밋을 확인해보니 주석에 **"왜 상수인가"(결정성)만 있고 "왜 이
  숫자인가"는 없었다.** 다른 값들은 근거가 남아 있었다 — 점프 13은 `sqrt(2*30*2.8)`,
  스킨 0.02는 부동소수점 관통 방지, 코요테 6틱은 100ms. 박스만 근거가 없는
  플레이스홀더였고, 근거 없는 값을 지키라고 권한 셈이 되어 논거를 다시 점검하다
  대역폭 논거가 성립하지 않는다는 것을 찾았다
- 수정: 정정하고 박스를 스프라이트에서 파생시키는 방향으로 전환했다. 그 과정에서
  튜닝을 절대 수치가 아니라 **캐릭터 키 대비 비율**로 관리하는 규칙이 나왔고,
  인스펙터에 진단 패널을 붙여 현재 값이 권장 범위 안인지 보이게 했다
- 남는 교훈: 어떤 값을 지키라고 권할 때는 **그 값에 근거가 있는지 먼저 확인해야
  한다.** 근거가 기록되어 있지 않다면 그것은 확정된 결정이 아니라 플레이스홀더이고,
  지킬 이유도 그만큼 약하다. 이 프로젝트가 결정마다 근거를 남기기로 한 이유가
  여기서 드러났다
