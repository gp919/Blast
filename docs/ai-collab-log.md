# AI 협업 로그

AI 도구를 개발에 활용하면서, **출력이 틀렸던 것과 그것을 어떻게 찾아 고쳤는지** 기록합니다.

"AI로 빠르게 만들었다"는 누구나 하는 말이라 어필이 약합니다.
**출력의 오류를 기술 이해로 잡아냈다**는 사례가 AI 친숙도와 기초 실력을 동시에 증명합니다.
자소서와 면접에서 쓸 근거를 여기에 모읍니다.

## 기록 기준

- 대상: 설계 판단 오류, 네트코드 로직 오류, 결정성 위반, 성능 함정
- 제외: 오타, 단순 컴파일 에러, API 이름 착오

## 작성 형식

```
### YYYY-MM-DD | 제목

- 맥락: 무엇을 만들고 있었나
- AI 출력: 무엇을 제안했나
- 문제: 왜 틀렸나 (원리 수준으로)
- 발견 경위: 어떻게 알아챘나
- 수정: 어떻게 고쳤나
```

**"발견 경위"를 반드시 쓰세요.** 면접에서 실제로 파고드는 건 이 부분입니다.

## 기록

### 2026-08-12 | 계층 경계가 asmdef 참조 그래프만으로는 지켜지지 않았음

- 맥락: NGO 스폰된 플레이어를 합성 루트(`Blast.Game`)의 틱 드라이버에 연결하는 중.
  "NGO 의존을 `Blast.Network` 안에 가둔다"를 이슈 #1 부터의 원칙으로 잡고 있었다
- AI 출력: 레지스트리가 `NetworkPlayer`(= `NetworkBehaviour` 파생)를 그대로 상위
  계층에 노출하는 설계. asmdef 참조 방향이 `Game -> Network` 라 규칙에 맞고,
  NGO 타입은 Network 어셈블리 밖으로 나가지 않는다고 설명했다
- 문제: **상속 체인 때문에 성립하지 않는다.** 상위 계층이 `NetworkPlayer` 를 변수로
  잡기만 해도 C# 컴파일러는 멤버 조회를 위해 기반 타입을 끝까지 해석해야 하고,
  그래서 `Unity.Netcode.Runtime` 참조를 요구한다(CS0012). NGO API 를 한 줄도
  쓰지 않아도 마찬가지다. 즉 "가뒀다"는 주장 자체가 틀렸다
- 발견 경위: 프리팹에 컴포넌트를 붙이려는데 Add Component 목록에 `Network Player`
  가 없었다. `.cs.meta` 는 생성되어 있었으므로 임포트는 됐다는 뜻이고, 컴파일이
  실패해 Unity 가 이전 어셈블리를 그대로 쓰고 있는 상황으로 좁혀졌다.
  `check-layering.ps1` 은 통과 상태였다. 참조 그래프는 정상이었고 깨진 것은
  컴파일이었기 때문이다
- 수정: NGO 타입을 상속하지 않는 평범한 클래스 `PlayerHandle` 을 두고, 스폰 시
  NGO 가 아는 값(`OwnerClientId`, `IsOwner`, `GameObject`)을 복사해 레지스트리에
  넣도록 바꿨다. `Blast.Game` 에 NGO 참조를 추가하는 선택지는 버렸다.
  그건 경계를 지키는 것이 아니라 경계가 깨진 것을 인정하는 쪽이다
- 남는 교훈: 자동 검사(`check-layering.ps1`)가 통과했다고 계층이 지켜진 것은
  아니다. 그 스크립트는 asmdef 참조 방향만 본다. **타입 노출면(어떤 타입이
  어셈블리 경계를 넘어가는가)은 검사 대상이 아니다**

### 예시 (첫 항목 작성 후 삭제)

**2026-08-15 | 재조정 되감기 시작 틱 오프셋 오류**

- 맥락: 서버 상태 수신 후 불일치 시 재시뮬레이션하는 로직 구현 중
- AI 출력: 수신한 서버 틱 번호부터 재시뮬레이션 시작
- 문제: 서버 스냅샷은 해당 틱 처리가 **끝난 뒤**의 상태이므로, 그 틱부터 다시 돌리면
  입력이 한 번 중복 적용됨. `serverTick + 1`부터 시작해야 함
- 발견 경위: RTT 150ms에서 계속 이동하면 캐릭터가 조금씩 앞서 나가는 현상.
  디버그 오버레이로 서버 위치와 예측 위치를 겹쳐 그려 편차가 누적되는 것을 확인
- 수정: 재시뮬레이션 시작 인덱스를 +1로 보정하고, 입력 버퍼에서 해당 구간만 재적용
