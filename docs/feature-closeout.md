# 기능 완료 절차

이슈 하나가 끝날 때마다 수행하는 마무리 절차입니다. 코드를 다 짠 시점이 아니라
**머지하고 다음 작업을 가리켜 둔 시점**이 완료입니다.

이 절차가 없으면 두 가지가 새어 나갑니다.

- 동작은 하는데 왜 그렇게 짰는지 설명할 수 없는 코드
- 이번에 처음 쓴 Unity 기능에 대한 이해가 다음 챗으로 이어지지 않는 것

작업자는 C++/DX11 자체 엔진 경험자이고 Unity와 C#은 이번이 처음입니다.
그래서 5번 항목이 다른 프로젝트에는 없는 단계입니다.

---

## 언제 수행하나

이슈 하나의 구현과 동작 확인이 끝난 시점입니다. 판단 기준은 하나입니다.

**그 이슈의 완료 조건 체크박스를 전부 채울 수 있는가.**

채울 수 없는 항목이 있으면 아직 완료가 아닙니다. 다만 **다른 이슈가 있어야
확인 가능한 항목**은 예외입니다. 그 경우 이월 사유를 PR 본문에 적고 넘어갑니다.
예: 이슈 #7 의 "입력 지연 체감"은 Network Simulator 배선이 필요해 2주차 C 로 이월.

---

## 절차

### 1. 완료 조건 확인

이슈의 체크박스를 하나씩 실제로 확인합니다. 코드를 읽어서가 아니라 **화면이나
콘솔에서** 확인합니다. `docs/project_context.md` 3번 관측 가능성 절의 원칙입니다.

확인 수단이 없는 항목이 있으면 그것부터 만듭니다. 관측 수단 없이 완료로
보고하지 않습니다.

### 2. 계층 검증

```powershell
powershell -ExecutionPolicy Bypass -File tools/check-layering.ps1
```

위반 0건이어야 합니다. **다만 이 스크립트가 통과했다고 계층이 지켜진 것은
아닙니다.** asmdef 참조 방향만 보고 타입 노출면은 보지 않습니다.
`docs/ai-collab-log.md` 2026-08-12 항목 참조.

### 3. 코드 리뷰

AI 에게 이번 작업에서 추가되거나 바뀐 코드의 리뷰를 요청합니다.
아래를 중점적으로 봅니다.

**넷코드 공통**

- 되감기 시작 틱 오프셋. 스냅샷이 그 틱 처리 전인가 후인가
- 버퍼 인덱싱. 링버퍼 랩어라운드, 오프바이원
- 순회 순서가 피어마다 같은가. `Dictionary` 순회, 등록 순서 의존
- `IsHost` 로 분기한 곳이 있는가. 서버 조건은 항상 `IsServer` 여야 한다
- 에지 입력의 수명. 소비 전에 덮어써지거나, 소비되지 않고 남거나

**Unity 및 C# 함정**

- 매 프레임 호출 경로의 GC 할당. `GetComponent`, 문자열 연결, 람다 캡처, 박싱
- `readonly` struct 필드에 상태 변경 메서드 호출. 방어적 복사가 조용히 일어난다
- `List<T>` 에 struct 를 담고 인덱서로 수정. 복사본이 수정되고 사라진다
- 이벤트 구독 해제 누락. 특히 `static` 이벤트
- `[SerializeField]` 에 시뮬레이션 상태 노출

**계층**

- 어셈블리 경계를 넘어가는 타입이 늘었는가. 참조 방향이 맞아도 노출면이 새면
  CS0012 로 컴파일이 깨진다

리뷰 결과 중 지금 고칠 것과 다음 이슈로 미룰 것을 나눕니다.

**결과는 `docs/notes/issue-NN-*.md` 에 남깁니다.** 6번 항목과 함께 한 파일에
씁니다. 지적된 것, 고친 것, 미룬 것을 상태와 함께 적고, 미룬 것은
`docs/notes/README.md` 의 미해결 표에도 한 줄 넣습니다. 그 표가 다음 챗이 보는
잔여 목록입니다.

### 4. AI 협업 로그

AI 의 출력이나 진단이 틀렸던 것이 이번 작업에 있었으면
`docs/ai-collab-log.md` 에 추가합니다. 기록 기준은 그 문서 상단 참조.

**"발견 경위"를 반드시 씁니다.** 면접에서 파고드는 것이 그 부분입니다.
특히 **어떤 조건에서 증상이 사라졌는가**는 원인을 좁힌 근거라 가치가 높습니다.

### 5. Unity 개념 대응 정리

**이 프로젝트에만 있는 단계입니다.**

이번 작업에서 처음 쓴 Unity 나 C# 기능을 정리하고, C++ 및 자체 엔진 개념에
대응시켜 설명을 받습니다. 대상은 아래 같은 것들입니다.

- 처음 쓴 Unity API 나 특성 (`[Rpc]`, `NetworkVariable`, `CustomEditor` 등)
- C++ 에 대응물이 없거나 동작이 다른 C# 문법 (값/참조 타입, 방어적 복사, GC)
- 엔진이 대신 해주는 것과 직접 해야 하는 것의 경계

목적은 **저장소에 작업자가 설명하지 못하는 코드를 남기지 않는 것**입니다.
`CLAUDE.md` 의 AI 활용 원칙 그대로입니다.

**설명은 3번의 리뷰 결과와 같은 파일에 남깁니다.**

```
docs/notes/issue-<번호 두 자리>-<짧은-영문-설명>.md
```

챗 안에서만 설명하고 끝내지 마세요. 나중에 다시 읽는 것이 목적이므로 파일로
남는 것이 이 단계의 산출물입니다. `docs/notes/README.md` 색인에 이슈 번호와
다룬 개념을 한 줄 추가합니다. 개념만 다시 찾아 읽을 때 그 표를 봅니다.

정리 결과 중 되풀이해서 걸릴 만한 것은 `docs/project_context.md` 의
저장소 특이사항에도 남깁니다. 그쪽은 새 챗이 오해하지 않기 위한 것이고,
노트는 작업자가 읽기 위한 것이라 분량과 어조가 다릅니다.

#### 5-1. 스크립트 파일별 설명

같은 파일에 **이번 이슈가 만들거나 고친 `.cs` 파일을 하나씩** 설명하는 절을 넣습니다.
개념 대응만으로는 "이 파일이 왜 따로 존재하는가"가 남지 않습니다.

파일마다 아래 셋을 씁니다.

- **왜 이 파일이 따로 있는가.** 합쳤다면 무엇이 깨지는가로 답합니다
- **핵심 코드 몇 줄과 그 줄이 막고 있는 실패**
- 해당하면 C++ 및 자체 엔진 대응물

먼저 **입력이나 상태가 파일들을 지나가는 경로를 그림으로** 넣고 그 순서대로
설명합니다. 파일 목록을 알파벳순으로 나열하면 왜 그 구조인지가 드러나지 않습니다.

이번 이슈가 손대지 않은 파일도 한 줄짜리 표로 붙입니다. 전체 지도가 있어야
새로 생긴 파일의 자리가 보입니다.

### 7. 커밋과 머지

`CLAUDE.md` 의 Git 운용 규칙을 따릅니다. AI 는 커밋 메시지 초안만 제시합니다.

- `.cs` 를 새로 만들었으면 **에디터를 한 번 활성화**해 `.cs.meta` 를 생성한 뒤 커밋
- 코드 커밋과 문서 커밋을 나눕니다. 한 커밋 안에서 파일이 겹치면 합쳐도 됩니다
- PR 본문에 완료 조건 체크박스와 이월 사유를 적습니다
- 머지 후 로컬 `main` 을 갱신합니다. **이것을 빠뜨리면 다음 챗이 옛 코드를 봅니다**

## 챗을 마무리하는 시점

아래 세 가지가 모두 참이면 그 챗은 끝난 것입니다.

1. 머지가 끝나고 로컬 `main` 이 `origin/main` 과 같다
2. `docs/project_context.md` 5번 현재 작업 항목이 다음 작업을 가리킨다
3. 다음 이슈가 생성되어 있다

이 외에 **컨텍스트가 길어져 요약이 반복되기 시작하면** 기능이 안 끝났어도
끊는 것을 고려합니다. 요약은 근거를 잃습니다. 왜 그렇게 정했는지가 사라지고
결론만 남으면 이 프로젝트에서는 손실이 큽니다.

### 종료 전 확인

```powershell
git status --short --branch
git log --oneline -3
```

- 작업 트리가 clean 한가
- 로컬이 `origin` 과 같은가. 다르면 `git pull` 또는 push
- 미커밋 문서 변경이 남아 있지 않은가

### 다음 챗 첫 메시지

새 챗은 `CLAUDE.md` 와 `docs/project_context.md` 를 읽고 시작합니다.
따라서 첫 메시지는 짧아도 됩니다.

```
이슈 #N 진행할게. 브랜치부터 만들어줘.
```

AI 는 브랜치 생성 전에 현재 브랜치가 `main` 이고 작업 트리가 clean 한지
확인해야 합니다. 아니면 중단하고 알립니다.

작업 기기가 바뀌었다면 첫 메시지에 그것을 적습니다. Unity 버전, Git LFS,
`gh auth` 상태를 먼저 확인해야 합니다.
