# 성능 노트 #1: 관측 도구가 관측 대상을 바꾼 문제

날짜: 2026-08-28
커밋: `7d3ab2f`
대응 이슈 없음. 이슈 #9 완료 후 이슈 #10 착수 전에 처리했습니다.

커스텀 인스펙터를 열어둔 것만으로 시뮬레이션이 틱을 버리고 있었습니다. 관측 수단이
관측 대상에 개입한 사례이고, 원인 코드는 이슈 #9 에서 진단 패널을 만들며 들어왔습니다.

---

## 1. 증상과 최초 가설

Play 중 캐릭터는 안정적으로 움직이는데, 스폰된 `Player(Clone)` 을 선택해 인스펙터를
띄우면 눈에 띄게 끊겼습니다. 인스펙터를 닫으면 돌아옵니다.

여기서 가설이 두 갈래로 갈립니다.

| 가설 | 예상되는 근거 | 사실이면 할 일 |
|---|---|---|
| 에디터 UI 비용 | 빌드에서는 재현되지 않는다 | 에디터 코드만 고치면 된다 |
| 게임 코드 결함 | 빌드에서도 재현된다 | 런타임 코드를 고쳐야 한다 |

두 가설은 고쳐야 할 대상이 완전히 다르므로, 코드를 보기 전에 어느 쪽인지부터
갈라야 했습니다.

## 2. 검증

`TickDriver` 인스펙터의 틱 수 표시와 프로파일러 두 가지로 확인했습니다.

프로파일러의 CPU Usage 그래프에서 인스펙터를 켠 시점을 경계로 그래프가 완전히
갈렸습니다.

```
켜기 전   대체로 16ms 선 아래. 간헐적 스파이크만 위로 튐
켠 후     66ms 선 위까지 통째로 채워짐. 상단 CPU 하이라이트 바가 연속 적색
```

**중요한 것은 어느 색으로 채워졌는가입니다.** `Rendering`, `Scripts`, `Physics` 가
아니라 `Others` 가 부풀었고, `EditorLoop` 가 이 카테고리에 집계됩니다. 게임 코드가
아니라 에디터 UI 가 시간을 쓰고 있다는 뜻이므로, 앞의 표에서 첫 번째 가설로 확정됩니다.
프레임을 클릭해 Hierarchy 뷰를 시간 내림차순으로 정렬하면 `EditorLoop` 가 최상단에
나오는 것으로 한 번 더 확인할 수 있습니다.

`TickDriver` 의 관측값도 정확히 맞아떨어졌습니다.

```
평소            이번 프레임 틱 수 0 ~ 1
인스펙터 켠 후   이번 프레임 틱 수 3 ~ 5
```

틱 하나가 16.667ms 이므로 3틱은 프레임 시간 50ms, 5틱은 83ms 에 해당합니다.
그래프가 66ms 선을 오르내린 것과 산술적으로 일치합니다. 서로 다른 두 관측
수단이 같은 결론을 가리켰으므로 측정 자체를 의심할 이유가 없어졌습니다.

한 가지 덧붙이면, 프로파일러는 켜져 있는 것만으로도 비용이 듭니다. 프레임마다
계측 마커를 기록하고 그래프를 다시 그리기 때문입니다. 다만 이번 측정에서는
비교 구간 양쪽 모두 프로파일러가 켜져 있었으므로, 차이분은 순수하게 인스펙터가
추가한 비용입니다. **프로파일러는 절대 수치를 재는 데는 부적합하지만 변인 하나만
바꿔 비교하는 데는 유효합니다.** 절대 수치가 필요하면 Development Build 에
Autoconnect Profiler 로 붙어야 합니다.

## 3. 원인

`PlayerPresenterEditor.OnInspectorGUI` 가 프레임마다 아래 경로를 탔습니다.

```
OnInspectorGUI -> TryLoadTuningAsset -> AssetDatabase.FindAssets("t:CharacterTuningAsset")
                                     -> AssetDatabase.GUIDToAssetPath
                                     -> AssetDatabase.LoadAssetAtPath
```

`AssetDatabase.FindAssets` 는 프로젝트의 애셋 데이터베이스 전체를 타입 조건으로
질의하는 호출입니다. 애셋이 하나뿐이라 결과가 항상 같은데도 60fps 기준 초당 60회
반복되었고, 프로젝트에 애셋이 늘어날수록 비용이 비례해 커지는 구조였습니다.

이것이 주된 원인이고, 같은 함수에 부차적인 요인이 셋 더 있었습니다.

| 요인 | 성격 |
|---|---|
| `RequiresConstantRepaint()` 가 Play 중 `true` | 갱신 빈도 자체가 초당 60회 |
| `Animator.parameters` | 호출마다 새 배열을 할당하는 프로퍼티. 매 프레임 GC 할당 |
| `serializedObject.FindProperty("_animator")` | 문자열로 프로퍼티를 찾는 비용을 매번 지불 |

## 4. 왜 단순한 프레임 저하가 아니었는가

이 부분이 이 노트를 남기는 이유입니다. 에디터가 느려지는 것으로 끝나지 않고
**시뮬레이션 결과가 실제로 달라졌습니다.**

`FixedTickAccumulator` 는 프레임 시간을 누적해 고정 틱을 뽑아냅니다. 프레임이
길어지면 밀린 틱이 늘어나는데, 그것을 무제한으로 돌리면 다음 프레임이 더 길어지는
death spiral 이 생기므로 `MaxTicksPerFrame` 을 5 로 제한하고 있습니다. 그리고
상한에 걸리면 남은 누산 시간을 버립니다.

```
프레임 83ms 초과  ->  밀린 틱 5개 초과  ->  상한 도달  ->  누산기 폐기
```

즉 인스펙터를 열어둔 상태에서는 **시뮬레이션 시간 자체가 사라지고 있었습니다.**
화면이 덜 부드러운 것이 아니라 캐릭터가 실제로 덜 움직인 것이고, 처음에 느낀
"렉 걸리는 것 같다"는 체감이 정확했습니다.

누산기의 폐기 동작 자체는 의도된 설계이고 그대로 두는 것이 맞습니다. 문제는
그 상한을 실제로 건드리는 원인이 관측 도구였다는 점입니다.

## 5. 해결

### 신규: `InspectorRepaintThrottle`

`EditorApplication.update` 에 붙어 0.1초 간격으로만 `Repaint()` 를 호출합니다.
두 커스텀 에디터가 공유합니다. 사람이 눈으로 읽는 값에 초당 60회는 필요하지 않고,
초당 10회면 충분합니다.

대상 오브젝트가 파괴된 뒤 `Repaint()` 를 부르면 예외가 나므로 막아두었고,
`OnDisable` 에서 반드시 구독을 해제하도록 짝을 맞췄습니다. **해제하지 않으면 파괴된
에디터 인스턴스를 가리키는 델리게이트가 에디터 전역 이벤트에 남습니다.**

### `PlayerPresenterEditor`

- `AssetDatabase.FindAssets` 를 `OnEnable` 한 번으로 옮겼습니다. 애셋 참조를 들고
  있으면 값 변경은 그대로 읽히므로, 다시 찾아야 하는 경우는 애셋이 새로 생성되거나
  삭제되었을 때뿐입니다. Play 중에는 재조회를 아예 막았습니다. 애셋을 찾지 못한
  프로젝트에서 매 프레임 전체 검색이 도는 것이 원래 코드의 최악 경로였습니다
- `Animator.parameters` 를 캐싱했습니다. 참조가 바뀔 때만 다시 읽습니다
- `SerializedProperty` 두 개를 `OnEnable` 에서 한 번만 조회합니다
- `RequiresConstantRepaint()` 를 제거하고 스로틀로 교체했습니다

### `TickDriverEditor`

같은 원인을 공유하므로 함께 처리했습니다. 다만 여기에는 갱신 간격을 늘리면
생기는 부작용이 있습니다. **초당 10회만 그리면 한 프레임 동안만 상한에 붙었다가
돌아오는 틱 수를 놓칩니다.** 관측 도구가 관측을 못 하게 되면 본말이 뒤바뀝니다.

그래서 표시와 관측을 분리했습니다.

```
그리기   0.1초 간격        InspectorRepaintThrottle
읽기     에디터 갱신마다   SampleTickCount (정수 비교 두 번)
```

- "관측 최대 틱 수" 항목을 추가했습니다. 표시 간격 사이에 지나간 최대치가 남습니다
- 상한 도달 경고를 순간값이 아니라 누적 기준으로 바꿨습니다. 한 번이라도 닿았으면
  계속 표시되고, 에디터 창 때문일 수 있다는 안내를 문구에 넣었습니다
- 기준점을 다시 잡는 "관측값 초기화" 버튼을 넣었습니다

에디터 갱신이 게임 프레임과 1대1로 대응한다는 보장은 없으므로 이 값은 표본입니다.
다만 인스펙터가 그려지는 시점에만 읽는 것보다는 훨씬 촘촘합니다.

## 6. Unity 및 C# 개념 대응

**IMGUI 는 즉시 모드입니다.** `OnInspectorGUI` 는 UI 트리를 만들어두고 바뀐 곳만
갱신하는 방식이 아니라, 호출될 때마다 레이아웃 계산과 위젯 배치를 처음부터 다시
합니다. DirectX 로 매 프레임 정점 버퍼를 새로 채워 그리는 것과 같은 구조입니다.
따라서 **그리는 함수 안에 무거운 조회를 두면 그 비용이 프레임마다 그대로 나옵니다.**
리테인드 방식 UI 를 가정하고 코드를 짜면 여기서 어긋납니다.

**`AssetDatabase` 는 에디터 전용 리소스 인덱스입니다.** `FindAssets` 는 그 인덱스에
질의를 던지는 호출이고, 자체 엔진으로 치면 매 프레임 리소스 매니페스트를 열어
전체를 훑어 핸들 하나를 얻는 것에 해당합니다. 결과가 변하지 않는 조회는 초기화
시점에 한 번 해두고 핸들을 보관하는 것이 원칙이며, 이 원칙은 엔진이 바뀌어도
그대로입니다.

**`Editor` 의 `OnEnable` 과 `OnDisable` 은 인스펙터 창의 수명주기입니다.**
대상 오브젝트의 수명이 아니라 **에디터 인스턴스의 수명**에 묶여 있습니다. 선택이
바뀌거나 도메인 리로드가 일어나면 인스턴스가 새로 만들어지고 `OnEnable` 이 다시
불립니다. 캐시를 채우는 자리이자, 전역 이벤트 구독을 해제해야 하는 자리입니다.
C++ 의 RAII 처럼 스코프를 벗어나며 자동으로 정리되지 않으므로 짝을 직접 맞춰야
합니다.

**`Animator.parameters` 처럼 매번 새 배열을 돌려주는 프로퍼티가 C# 에 흔합니다.**
이름이 필드처럼 보여서 비용이 없어 보이지만 실제로는 할당이 일어납니다. 게터가
내부 배열의 복사본을 돌려주는 C++ 코드와 같고, 호출부에서는 구분이 되지 않습니다.
프로퍼티라는 이유로 반복 호출해도 된다고 판단하면 안 됩니다.

**`Time.time` 과 `EditorApplication.timeSinceStartup` 은 다른 시계입니다.**
후자는 에디터의 벽시계라 타임스케일과 무관하며, 게임을 일시정지해도 계속 흐릅니다.
스로틀에 이것을 쓴 이유는 일시정지 중에도 인스펙터 갱신은 이어져야 하기 때문입니다.

## 8. 남은 한계

- **에디터 UI 비용이 0 이 되지는 않습니다.** 인스펙터를 띄우면 여전히 비용이 들므로,
  프레임 예산을 진지하게 판단할 때는 창을 닫아야 합니다. 이슈 #10 의 기준선 측정도
  같은 조건을 지켜야 합니다
- 표시 항목마다 발생하는 `ToString` 과 보간 문자열 할당은 남겨두었습니다. 갱신 빈도가
  6분의 1 로 줄어 실질적인 부담이 사라졌고, 더 줄이려면 문자열 캐시가 필요한데
  그 복잡도를 낼 자리가 아닙니다
- MPPM 가상 플레이어는 각각 별도 에디터 프로세스입니다. 양쪽 인스펙터를 동시에
  열면 비용도 그만큼 늘어납니다
